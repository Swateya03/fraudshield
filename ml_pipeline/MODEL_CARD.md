# FraudShield Model Card

## Overview

| Field | Value |
|-------|-------|
| **Model type** | XGBoost binary classifier (Card-Not-Present fraud detection) |
| **Task** | Predict the probability that a transaction is fraudulent |
| **Output** | `fraud_probability` ∈ [0, 1] + decision label (ALLOW / REVIEW / BLOCK) |
| **Inference latency** | < 50 ms p99 (including feature computation) |
| **Fallback** | Rule-based strategy when no trained model is present in the registry |

---

## Training Data

| Property | Detail |
|----------|--------|
| **Source** | Synthetic transactions generated by `ml_pipeline/data/simulator.py` |
| **Size** | ~10,000 transactions per training run (configurable) |
| **Time range** | 90-day rolling window |
| **Label rate** | ~8% fraud, ~12% suspicious, ~80% legitimate |
| **Split strategy** | `GroupShuffleSplit` on `user_id` — prevents entity leakage between train and test sets |
| **Known limitation** | Trained on synthetic data. Performance on real-world production traffic will differ until enough labelled chargebacks are collected via the `/v1/labels` feedback loop. |

## Features (21 total)

### Amount features — normalised to INR before computation
| Feature | Description |
|---------|-------------|
| `log_amount` | log1p(amount_inr) — compresses the long tail |
| `amount_ratio` | amount_inr / user's historical average amount |
| `amount_zscore` | (amount_inr − user_avg) / user_std |
| `is_round_amount` | 1 if amount is a multiple of 100, else 0 |

### Time features
| Feature | Description |
|---------|-------------|
| `hour_of_day` | 0–23 |
| `day_of_week` | 0 = Monday, 6 = Sunday |
| `is_weekend` | 1 if Saturday or Sunday |
| `is_night` | 1 if hour ∈ [0, 5] |

### Velocity features (Redis-backed, real-time)
| Feature | Description |
|---------|-------------|
| `velocity_1h` | Transactions by this user in the last 1 hour |
| `velocity_24h` | Transactions by this user in the last 24 hours |
| `velocity_7d` | Transactions by this user in the last 7 days |
| `user_avg_amount` | Rolling average transaction amount for this user |
| `user_std_amount` | Rolling standard deviation of amount for this user |

### Device / identity features
| Feature | Description |
|---------|-------------|
| `device_age_days` | Days since device was first seen |
| `is_new_device` | 1 if device first seen in the last 7 days |
| `is_known_ip` | 0 if IP is on the fraud IP list, else 1 |

### Risk signal features
| Feature | Description |
|---------|-------------|
| `merchant_risk` | 1.0 = high-risk merchant, 0.5 = medium, 0.2 = standard |
| `ip_risk` | 1.0 if IP on blocklist, else 0.0 |
| `user_risk_tier` | Encoded: blocked=1.0, high=0.75, medium=0.5, low=0.0 |
| `kyc_status` | Encoded: verified=0.0, pending=0.5, failed=1.0 |
| `channel_risk` | online=1.0, upi=0.6, atm=0.4, pos=0.2, nfc=0.1 |

## Decision Thresholds

Two thresholds partition the [0, 1] probability output into three labels:

```
0.0 ──────────────── 0.50 ──────────────── 0.85 ──── 1.0
        ALLOW               REVIEW               BLOCK
```

| Label | Condition | Meaning |
|-------|-----------|---------|
| ALLOW | score < 0.50 | Low risk — transaction proceeds |
| REVIEW | 0.50 ≤ score < 0.85 | Medium risk — flag for analyst review |
| BLOCK | score ≥ 0.85 | High risk — transaction declined |

### Why these thresholds?

The 0.85 / 0.50 split was chosen by plotting the precision-recall curve on the held-out test set and selecting the operating point that satisfies:

- **BLOCK (0.85):** precision ≥ 0.90 — fewer than 1 in 10 blocks is a false positive. Prioritises customer experience over fraud capture rate.
- **REVIEW (0.50):** recall ≥ 0.85 — catches at least 85% of fraud cases for manual review. Prioritises fraud capture; analysts triage the queue.

Both thresholds are configurable via env vars (`FRAUD_THRESHOLD`, `REVIEW_THRESHOLD`) so they can be adjusted without redeployment as the model is retrained on production labels.

## Known Limitations

1. **Synthetic training data** — the model has not been validated on real-world production transactions. Precision and recall figures above are optimistic estimates.
2. **Static FX rates** — currency normalization uses fixed exchange rates (`FX_USD`, `FX_EUR` env vars). Stale rates introduce a systematic amount bias.
3. **No concept drift detection** — PSI monitors feature distribution shift, but the model is not automatically retrained when performance degrades. Monitor precision/recall on analyst-labelled transactions weekly.
4. **Cold-start users** — new users have no velocity history (`velocity_*` = 0, `user_avg_amount` = 0). The model falls back to merchant/channel/IP signals; scores for first-time users may be unreliable.
5. **Channel risk is heuristic** — `channel_risk` values (online=1.0, nfc=0.1) are expert-assigned. Validate against actual chargeback rates once production data is available.
